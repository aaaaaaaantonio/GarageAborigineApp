# CRM Telegram-бот — стек экранов, компактные карточки, Redis: спецификация

Дата: 2026-10-04
Статус: согласовано, к планированию
Дополняет: `docs/superpowers/specs/2026-10-02-crm-bot-navigation-design.md`
Ветка: поверх `search-fixes` (пагинация поиска переделывается здесь же)

## Контекст

Сверено с кодом на `search-fixes` d824400:

1. **Карточка заезда перегружена.** `bot/handlers/visits.py: send_visit_card` рисует
   на каждую работу 3–5 кнопок (`✅`, `🔄 → статус`, `🔧 запчасть`, `👤 исполнитель`).
   С двумя-тремя работами экран — стена кнопок.
2. **Нет «назад».** Каждый экран — новое сообщение (`message.answer`), вернуться
   на предыдущий экран нельзя; чат копит сообщения со старыми кнопками.
3. **Две навигации.** Reply-меню (`bot/keyboards.py`) занимает полэкрана и живёт
   параллельно inline-кнопкам.
4. **Мастера без шага назад.** Опечатка на 4-м шаге — только `/cancel` и заново.
5. **FSM в памяти.** `MemoryStorage` (`bot/main.py`): любой перезапуск/деплой
   обрывает начатые мастера; следующий текст пользователя уходит в поиск.
6. **«Мои работы» у механика** — отдельное сообщение на каждую работу с сырым uuid
   заезда (`bot/handlers/mechanic.py`).

Цель: один «живой» экран, который меняется на месте; из любого экрана — назад туда,
откуда пришёл, или в меню; карточки компактные; состояние переживает деплой.

## Решения (согласованы)

- Свой стек экранов (не aiogram-dialog).
- Экраны **редактируют одно сообщение на месте** (`edit_text`).
- **Reply-меню убирается.** Корень стека — inline-меню; запасной вход — `/menu`.
- В мастере `‹ Назад` — **шаг назад** (данные сохраняются); `✖ Отмена` — на
  экран-источник.
- FSM-хранилище — **Redis** (`RedisStorage`).

## 1. Механика стека

### Экран

Экран = имя + параметры, напр. `("visit", {"id": "<uuid>"})`. Реестр
`name → render(api, user, args) -> (text, InlineKeyboardMarkup)`. Рендер каждый раз
запрашивает свежие данные из API.

### Состояние (FSM data)

- `nav_stack: list[[name, args]]` — на дне всегда `["menu", {}]`.
- `nav_msg_id: int | None` — id живого сообщения.

### callback_data

| Префикс | Смысл |
|---|---|
| `go:<screen>[:<id>[:<id2>]]` | положить экран в стек, отрисовать |
| `back` | снять верх, отрисовать новый верх |
| `home` | стек := `[menu]`, отрисовать |
| `act:<name>[:<arg>]` | действие; контекст (заезд, работа) берётся из параметров **верхнего экрана**; после — перерисовать верх (или снять подэкран, см. §2) |

id кодируются `bot/callback_ids.encode_id` (22 символа). Самый длинный `go:` —
экран работы: `go:work:<22>:<22>` ≈ 51 байт (лимит 64). `act:` несёт максимум
один id.

### Отрисовка

1. Нажатие кнопки → `edit_text` сообщения, на котором нажали; оно становится живым.
2. Новое сообщение отправляется, когда: экран вызван после текстового ввода;
   `/start`, `/menu`; редактирование не удалось.
3. Новое сообщение становится живым; у прежнего живого снимается клавиатура
   (`edit_reply_markup(None)`) — устаревших кнопок в истории не остаётся.
4. Экран кладётся в стек **только после успешного рендера**.

Нижний ряд каждого экрана, кроме меню: `‹ Назад · 🏠 Меню`.

### Прочее

- `back` при пустом/отсутствующем стеке → меню.
- Свободный текст вне мастера — поисковый запрос (как сейчас); результаты
  открываются экраном `search_results` поверх текущего стека.
- Модуль `bot/nav.py`: стек, реестр, рендер, роутер `go/back/home`. Экраны
  регистрируются из существующих файлов `bot/handlers/*`.
- Удаляется `bot/keyboards.py` (reply-клавиатура). `bot/handlers/menu.py` остаётся,
  но держит экран `menu` и временный обработчик старых текстов (§6).

## 2. Карта экранов

Иконки статуса работы: ⏳ `not_ready`, 🔧 `in_progress`, 📦 `waiting_parts`,
✅ `ready` — в `bot/work_item_status.py`.

| Экран | Параметры | Текст | Кнопки |
|---|---|---|---|
| `menu` | — | приветствие | MASTER/ADMIN: `🆕 Новый заезд`, `🔧 Заезды в работе`, `🔍 Поиск`, `📝 Регистрация клиента (бумага)`; ADMIN ещё `👥 Добавить сотрудника`. MECHANIC: `🧰 Мои работы`, `🔍 Поиск`. Без «Назад» |
| `active_visits` | — | «Заезды в работе (N)», пометка об усечении | по заезду: `⭐ А123ВС · Иванов · Ремонт` → `visit` |
| `visit` | visit id | шапка (`visit_header`) + нумерованный список работ: `1. Замена масла — В работе · Петров` | по работе: `🔧 1. Замена масла · Петров` → `work`; `➕ Добавить работу`; `🔄 Статус заезда` → `visit_status`; `📄 PDF` |
| `visit_status` | visit id | «Сменить статус заезда» | допустимые статусы (`_NEXT_STATUS_BY_CURRENT`); выбор → смена → **снять подэкран**, показать `visit`. «Отменён» → мастер причины |
| `work` | visit id, item id | название, статус, исполнитель, согласовано/нет | `✅ Согласовано клиентом` (если нет); переходы статуса (`NEXT_WORK_ITEM_STATUSES`); `🔩 Добавить запчасть`; `👤 Сменить исполнителя` → `reassign`. MECHANIC — только переходы статуса. Действие → перерисовать на месте |
| `reassign` | visit id, item id | «Кому передать работу?» | механики + `Без исполнителя`; выбор → назначение → снять подэкран, показать `work` |
| `my_works` | — | «Мои работы (N)» / «нет назначенных работ» | по работе: `🔧 Замена масла · А123ВС` → `work` |
| `search` | — | подсказка по роли | только нижний ряд; ввод текста → `search_results` |
| `search_results` | query, page | «Найдено: N · стр. p/P» | клиенты/машины → `client`/`vehicle`; `‹ ›` меняют `page` верхнего экрана на месте (без push) |
| `client` | client id | ФИО, телефон | машины → `vehicle`; `📋 Заезды клиента` → `visit_history` |
| `vehicle` | vehicle id | авто, VIN, пробег | как сейчас (`send_vehicle_card`): владелец → `client`, `📋 Заезды по машине`, `➕ Новый заезд` (мастер), `🔧 История работ` |
| `visit_history` | client id или vehicle id | «Заезды (N)» | заезды с датой → `visit` |
| `work_history` | vehicle id | история работ (как сейчас) | только нижний ряд |

`📄 PDF` отправляется отдельным документом; живое сообщение не меняется.

**Изменение бэкенда (единственное):** `WorkItemMineOut`
(`app/modules/visits/work_items_schemas.py`) получает `plate_number` и
`make_model` — для подписи кнопок `my_works` и шапки экрана `work` у механика
(механику `GET /visits/{id}` недоступен). Экран `work` у механика берёт работу
из `GET /work-items/mine`; у мастера/админа — `GET /visits/{id}` +
`GET /visits/{id}/work-items`.

**Не меняется:** уведомления механикам о назначении (шлёт бэкенд, без кнопок);
команды `/new_client`, `/new_vehicle` (по завершении — меню).

## 3. Мастера

### Модель

Мастер — цепочка шагов на FSM-состояниях (`bot/states.py`, как сейчас).
Дополнительно в FSM data:

- `wiz_steps: list[str]` — история пройденных шагов (имена состояний). Нужна,
  т.к. шаги ветвятся: справочник/своя формулировка, клиент найден/нет, ADMIN
  выбирает мастера/MASTER нет.
- данные мастера — как сейчас (`visit_id`, `mileage`, …).

Каждый шаг описан функцией «показать подсказку шага» (текст + кнопки выбора, если
есть) — её вызывают и при движении вперёд, и при `‹ Назад`.

### Кнопки

На каждом шаге: `‹ Назад · ✖ Отмена` (callback `wiz_back`, `wiz_cancel`).

- `wiz_back`: снять шаг из `wiz_steps`, установить предыдущее состояние, показать
  его подсказку. Введённые данные не стираются; новый ввод перезаписывает.
  На первом шаге = `wiz_cancel`.
- `wiz_cancel`: очистить состояние и данные мастера (стек не трогать), отрисовать
  верх стека — экран, откуда мастер запущен.

### Сообщения

- Шаг после нажатия кнопки — `edit_text` живого сообщения.
- Шаг после текстового ввода — новое сообщение (становится живым, у старого
  снимаются кнопки).
- Ошибка ввода — новое сообщение: подсказка шага + строка ошибки
  («Введите число (пробег в км).»).

### Завершение

| Мастер | Результат |
|---|---|
| Добавить работу, добавить запчасть, отмена заезда (причина) | верх стека (карточка `visit` / `work`) перерисован новым сообщением |
| Новый заезд | в стек кладётся `visit` нового заезда (источник + заезд) |
| Новый сотрудник, бумажное согласие, `/new_client`, `/new_vehicle` | строка-подтверждение + `menu` |

### Подпотоки

«Клиент не найден → завести клиента» и «машина не найдена → завести машину» —
шаги мастера нового заезда; хак `return_flow` (`bot/handlers/clients.py`,
`bot/handlers/vehicles.py`) заменяется именем мастера `wiz_name`, которое задаёт
старт мастера. `/new_client` и `/new_vehicle` используют те же функции шагов.
После создания сущности (клиент, машина) история шагов сбрасывается: «Назад»
не может повторить создание и на следующем шаге работает как «Отмена».

### Выбор из списка — экран, не мастер

«Сменить исполнителя» (`reassign`) и «Статус заезда» (`visit_status`) — подэкраны
стека; `ReassignMechanicStates` удаляется. Контекст действия — из параметров
верхнего экрана, поэтому `visit + item + mechanic` больше не нужно умещать в один
callback.

### Прерывание

`/menu`, `/start`, `/cancel` в любой момент очищают мастер. `/menu` и `/start` —
меню новым сообщением; `/cancel` — верх стека новым сообщением. Любой другой текст
в мастере идёт мастеру.

## 4. Хранилище: Redis

- `docker-compose.yml`: сервис `redis` (`redis:7-alpine`,
  `command: redis-server --appendonly yes`, том `redisdata`, healthcheck
  `redis-cli ping`). `bot` — `depends_on: redis: condition: service_healthy`,
  `environment: REDIS_URL: redis://redis:6379/0`.
- `bot/config.py`: `redis_url: str = ""`. Пусто → `MemoryStorage` (тесты, локальный
  запуск без Docker); задано → `RedisStorage.from_url(..., state_ttl=30 дней,
  data_ttl=30 дней)`.
- `pyproject.toml`: зависимость `redis>=5`.

## 5. Ошибки

| Ситуация | Поведение |
|---|---|
| `ApiError` при рендере `go:` / `act:` (404, 403) | `callback.answer(текст, show_alert=True)`, стек не меняется |
| `ApiError` при рендере по `back` | меню, текст ошибки строкой над ним |
| `TelegramBadRequest: message is not modified` | игнор, `callback.answer()` |
| Редактирование не удалось (сообщение удалено/старое) | отправить новое, сделать живым |
| Снятие кнопок со старого живого не удалось | игнор, `logger.debug` |
| `go`/`back`/`home` в неживом сообщении | обрабатывается; это сообщение становится живым |
| `act:` в неживом сообщении или не на своём экране | «Кнопка устарела» (контекст берётся из стека — чужой выполнять нельзя) |
| Права | роль решает, какие кнопки рисовать; бэкенд проверяет сам |

`ErrorHandlingMiddleware` остаётся для ошибок вне рендера экранов.

## 6. Выкатка

- Старые callback (`visit_open:`, `wsc:`, `wsm:`, `add_work:`, …) → `fallback`
  («Кнопка устарела — начните действие заново.»).
- Старые тексты reply-меню («Новый заезд», «Поиск», …) — отдельный временный
  обработчик: сообщение с `ReplyKeyboardRemove` + `menu`. Иначе текст ушёл бы в
  поиск. `/start` делает то же. Обработчик удаляется позже отдельным коммитом.
- `BOT_COMMANDS` (`bot/main.py`): добавить `menu` — «Главное меню».
- Порядок роутеров (`setup_routers`): `start` (команды) → временный legacy-menu →
  `nav` → мастера и экраны → `search` (свободный текст) → `fallback` (последний).

## 7. Тестирование

Стиль существующих `tests/bot/*`: mock-сообщения/callback, fake api.

- `bot/nav`: push/pop/home; `back` при пустом стеке; коммит стека только после
  успешного рендера; снятие клавиатуры у прежнего живого; запасной путь «отправить
  новое»; `message is not modified` не роняет.
- Рендер каждого экрана: текст и кнопки по ролям (у MECHANIC на `work` только
  статусы; у MASTER на `vehicle` есть «Новый заезд»).
- Каждый мастер: `wiz_back` по шагам, включая ветки; `wiz_cancel` → экран-источник;
  завершение по таблице §3.
- Все варианты callback_data ≤ 64 байт при максимальной длине id.
- Выбор хранилища: `redis_url` пуст → `MemoryStorage`, задан → `RedisStorage`
  (без живого Redis).
- Бэкенд: `/work-items/mine` отдаёт `plate_number`, `make_model`.
- Переписать: `test_routing.py` (новый порядок), тесты с `message.answer` → `edit_text`;
  удалить `test_keyboards.py`.
- После деплоя — ручная проверка в Telegram: мастер (заезд → работа → статус → назад),
  механик (мои работы → статус), деплой посреди мастера — мастер продолжается.

## Вне рамок

- Удаление сообщений пользователя после ввода.
- Кнопки в уведомлениях механикам.
- Web/Mini App.
