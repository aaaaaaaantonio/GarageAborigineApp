# CRM автосервиса — Telegram-бот: спецификация

Дата: 2026-09-19
Статус: утверждено к реализации

## Контекст

Backend (Этап 1) реализован, смёржен в `main`, захарднен (см.
`docs/superpowers/specs/2026-09-15-crm-backend-design.md`). Этот документ
описывает следующий цикл — Telegram-бот (aiogram 3), тонкий клиент поверх
готового API. Бизнес-логика остаётся только в `app/modules/*/service.py`;
бот не имеет прямого доступа к БД, только HTTP к CRM API — тот же принцип,
что и у будущего веб/Mini App.

## Аудитория и охват

Бот — рабочий инструмент **только для персонала** (ADMIN/MASTER/MECHANIC).
Клиентский Telegram-бот (уведомления клиентам, self-service) — если
понадобится, будет отдельным ботом, не смешивается с этим, чтобы не
путать роли и токены.

Охват — полный сразу, без урезанного MVP-подмножества: клиенты, авто,
заезды со статусной FSM, работы/запчасти, PDF-документы, поиск,
paper-регистрация consent, создание сотрудников (ADMIN), уведомления.
QR/веб-флоу согласия (`consent/draft`+статическая веб-страница) остаётся
как есть — бот в нём не участвует.

## Доработки backend в этом цикле

Три небольших добавления к уже реализованному Этапу 1, до начала работы над
самим ботом:

1. **`GET /users/by-telegram/{telegram_id}`** — резолвит входящий
   Telegram user id в `UserOut | 404`. Нужен боту на каждый апдейт, чтобы
   определить, кто пишет, и его роль. Источник правды — CRM (`users.telegram_id`,
   уже существующее поле), не отдельный маппинг внутри бота.
2. **`GET /work-items/mine`** — новый роутер без префикса `/visits/{visit_id}`
   (кросс-визитная выборка). Возвращает `VisitWorkItem[]`, где
   `assigned_mechanic_id == acting_user.id`, каждый элемент включает
   `visit_id`. Доступ: `require_role(MECHANIC)`. Закрывает пробел — раньше
   способа получить "мои назначенные работы" не было, только
   `PATCH .../status` по известному `item_id`.
3. **`TelegramNotificationSender`** (`app/modules/notifications/`) —
   реализация `NotificationSender` поверх `aiogram.Bot(token=...).send_message(chat_id=user.telegram_id, text=...)`.
   Подставляется вместо `LoggingNotificationSender` в
   `VisitService`/`WorkItemService` через конфиг. `aiogram` становится
   основной (не dev) зависимостью backend — сознательный выбор ради
   переиспользования `Bot`-клиента, если в бэкенд позже добавится что-то ещё
   Telegram-специфичное (например, отправка PDF-документа файлом), не
   переделывать транспорт заново. `LoggingNotificationSender` остаётся
   (тесты, фоллбэк если `telegram_id is None`).

## Архитектура бота

Отдельный top-level пакет `bot/`, рядом с `app/`, отдельный процесс
(aiogram long polling — без webhook/HTTPS-инфраструктуры на MVP):

```
bot/
  main.py                   # entrypoint, Dispatcher, polling
  config.py                 # BOT_TOKEN, API_BASE_URL
  api_client.py             # httpx.AsyncClient обёртка над CRM API,
                             # X-User-Id из auth-middleware, единая точка
                             # маппинга HTTP-ошибок в текст
  middlewares/
    auth.py                 # resolve telegram user -> CRM User через
                             # GET /users/by-telegram/{id}, кладёт в data["user"]
  handlers/
    start.py                 # /start, главное меню (пункты по роли)
    clients.py                # создание/поиск клиента
    vehicles.py                # создание/поиск авто, привязка владельца
    visits.py                   # визард нового заезда, карточка заезда
                                 # с inline-статусами
    work_items.py                # добавление работы (catalog/suggest →
                                  # кнопки), смена статуса, approve
    part_items.py                 # добавление запчасти
    documents.py                   # генерация/получение PDF
    search.py                       # поиск клиент/авто
    consent.py                       # paper-регистрация клиента
    admin.py                          # ADMIN: создание сотрудников
    mechanic.py                        # MECHANIC: "мои работы"
                                        # (GET /work-items/mine)
  states.py                  # FSM State-группы, по одной на визард
  keyboards.py                # переиспользуемые inline/reply-клавиатуры
```

## Аутентификация / middleware

- `middlewares/auth.py` работает на каждый апдейт: берёт
  `event.from_user.id`, вызывает `GET /users/by-telegram/{telegram_id}`.
  - Не найден или `deleted_at is not None` → ответ "Обратитесь к
    администратору, ваш Telegram не привязан", хендлеры не вызываются.
  - Найден → `User` (id, role) кладётся в `data["user"]`, доступен во всех
    хендлерах.
- `api_client.py` подставляет `user.id` в заголовок `X-User-Id` на каждый
  запрос к CRM API — та же MVP-схема доверенного заголовка, что и у
  остального backend (не меняется и не дублируется в боте).
- Ролевые проверки не дублируются в боте: бот только скрывает пункты меню,
  недоступные роли; финальную проверку всегда делает `require_role` на
  backend — единый источник правды.

## UX: меню + FSM-визарды + inline-кнопки

Полный набор действий через команды с аргументами (UUID/VIN/телефон руками)
нереалистичен для персонала — выбран вариант с постоянным Reply-меню,
пошаговыми FSM-визардами (aiogram `FSMContext`, `MemoryStorage` — один
инстанс бота на MVP, рестарт сбрасывает недописанный визард, ничего
критичного вне БД не хранится) и inline-кнопками для выбора сущностей и
статусов.

Каждый визард — конечный, с кнопкой/командой "Отмена" на любом шаге (сброс
state, возврат в меню). State-группы: `NewVisitStates`, `NewClientStates`,
`NewVehicleStates`, `AddWorkItemStates`, `AddPartItemStates`,
`NewStaffStates`.

## Сценарии по ролям

**ADMIN** — всё, что MASTER, плюс:
- Создание сотрудника: визард роль → ФИО → telegram_id (опционально) →
  `POST /users`.

**MASTER** — основной рабочий поток:
- Новый заезд: найти/создать клиента (`GET /search` по телефону, либо
  форма создания) → найти/создать авто (VIN/номер, либо форма) → пробег →
  выбор мастера (себя по умолчанию) → `POST /visits`.
- Карточка заезда: список работ/запчастей, inline-кнопки статуса (только
  разрешённые FSM-переходы, `PATCH /visits/{id}/status`), кнопка
  "Сформировать PDF" (`POST /visits/{id}/document`), кнопка "Согласовать
  работу" (`POST /work-items/{id}/approve`).
- Добавить работу: текст → `GET /catalog/suggest` → 3 кнопки-подсказки или
  "своя формулировка" → `POST /work-items`.
- Добавить запчасть: выбор `work_item` из списка заезда → форма
  (название/кол-во/цена) → `POST /part-items`.
- Paper-регистрация клиента (`POST /consent/paper`) — для клиентов без
  QR-флоу.
- Поиск (`GET /search`) из меню — текст → карточки клиент+авто.

**MECHANIC** — узкий поток:
- "Мои работы" — `GET /work-items/mine`, список назначенных работ со
  ссылкой на заезд.
- Смена статуса своей работы кнопками (`PATCH /work-items/{id}/status`).

## Обработка ошибок

Единая точка — декоратор/обёртка вокруг `api_client`, не размазано по
хендлерам:
- `404` → "Не найдено" + конкретика по контексту хендлера (клиент/авто/
  заезд/работа).
- `409` (недопустимый переход статуса, `NotAllWorkItemsReady`, дубликат
  consent) → текст причины из `detail`, без техжаргона.
- `422` (валидация, `InvalidAssignedMaster` и т.п.) → текст из `detail`.
- `5xx` / сеть недоступна → "Сервис временно недоступен, попробуйте
  позже" + лог для админа бота.

## Тестирование

- `api_client.py` — юнит-тесты с замоканным HTTP (respx/httpx mock) на
  маппинг ошибок.
- Хендлеры — тесты через aiogram test-утилиты (эмуляция апдейтов) на
  happy path каждого визарда + отмену на середине.
- `TelegramNotificationSender` — юнит-тест на формирование запроса
  (мокаем Telegram API), реальный Telegram в тестах не дёргаем.
- Ручной smoke — реальный бот в тестовом чате перед мержем, аналогично
  backend-циклу.

## Вне рамок этого документа

- Клиентский Telegram-бот (уведомления/self-service клиентам) — отдельный
  бот, отдельный цикл, если понадобится.
- Webhook-деплой, горизонтальное масштабирование бота (Redis FSM storage) —
  не нужно на MVP с одним инстансом.
- Веб/Mini App, клиентский контур — Этапы 2–3 (см. backend-спек).
